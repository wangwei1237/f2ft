# 开发流程规则

本文档约束 Agent 在本仓库中处理开发需求的流程。每个需求都必须按顺序经过三个阶段：整理需求文档、用户确认、开发并提交测试报告。任何阶段都不能跳过。

适用范围：新功能、功能修改、缺陷修复等需要改动代码或资源的需求。纯问答、代码解释、只读排查不需要走这个流程。

## 1. 整理需求文档

收到需求后，先不改代码，把用户的描述整理成标准需求文档。

**存放位置与命名**

- 目录：`requirements/`
- 文件名：`YYYYMMDD-NN-简短名称.md`
  - `YYYYMMDD` 是创建日期，例如 `20261113`。
  - `NN` 是当天的序号，从 `01` 开始，按 `requirements/` 中同一天已有的文档递增。
  - 简短名称用英文小写和连字符，例如 `20261113-01-translate-model-fix.md`。
- 已有的历史文件（如 `产品需求.md`）不改名，作为参考资料。

**文档模板**

```markdown
# <需求标题>

- 编号：YYYYMMDD-NN
- 状态：待确认 | 已确认 | 已完成
- 版本：v1
- 创建日期：YYYY-MM-DD
- 确认记录：（用户确认后填写，例如 "v1 于 2026-11-13 确认"）

## 背景
为什么要做，用户原话或问题现象。

## 目标
完成后用户能做到什么。

## 需求范围
- 要做的内容，逐条列出。

## 不在范围内
- 明确不做的内容。

## 验收标准
1. 可验证的条件，每条对应测试报告里的一个测试用例。

## 影响范围
预计修改的模块或文件。

## 待确认问题
需要用户回答的问题；没有则写"无"。
```

**要求**

- 内容来自用户的描述和现有代码事实，不自行添加用户没要求的功能。不确定的地方写进"待确认问题"，不要猜。
- 验收标准必须能通过操作和截图验证，避免"体验良好"这类无法检验的描述。

## 2. 用户确认

- 需求文档写好后，把文档路径和要点发给用户，明确请用户确认。此时文档状态为"待确认"。
- 只有用户明确表示确认（例如"确认""可以开始开发"）后，才能进入开发环节。用户没有回复、只提问题或只提修改意见，都不算确认。
- 确认后，把状态改为"已确认"，并在"确认记录"中写明确认的版本和日期。
- 每次修改需求文档（无论是用户要求修改，还是开发中发现需求需要调整），都要：
  1. 版本号加一（v1 → v2），状态改回"待确认"。
  2. 在文档末尾的"变更记录"中写明改了什么、为什么改。
  3. 再次请用户确认。确认之前，暂停与修改内容相关的开发工作。
- 开发中如果发现必须超出已确认范围才能完成，先停下来修改需求文档并请用户确认，不要直接扩大改动。

## 3. 开发与测试报告

**开发**

- 只实现已确认文档中的内容，遵守 `AGENTS.md` 中的代码约定、安全与隐私规则。
- 开发完成后，先确保构建通过（命令见 `AGENTS.md`）。

**测试**

- 按需求文档中的每一条验收标准逐项测试修改内容，并覆盖可能受影响的已有功能。
- 每个测试用例都必须有截图作为证据。没有截图的用例视为未测试。
- 截图优先用真机：`adb shell screencap -p /sdcard/shot.png` 后 `adb pull` 到本地。界面无法截图的结果（如服务端返回的错误信息），截取能显示该结果的界面或终端输出。
- 截图中不得出现 API Key、Token 等敏感信息。设置页截图时 Key 输入框必须保持隐藏状态。

**测试报告**

- 存放位置：`requirements/YYYYMMDD-NN-简短名称/test-report.md`，截图放在同目录的 `screenshots/` 下，文件名带用例编号，例如 `screenshots/TC01-connection-success.png`。
- 报告模板：

```markdown
# 测试报告：<需求标题>

- 需求文档：../YYYYMMDD-NN-简短名称.md（v<版本>）
- 测试日期：YYYY-MM-DD
- 测试环境：设备型号、Android 版本、App 版本、模型
- 结论：通过 | 部分通过 | 不通过

## 测试用例

### TC01 <用例名称>
- 对应验收标准：第 1 条
- 步骤：
  1. ...
- 预期结果：...
- 实际结果：...
- 结果：通过 | 不通过
- 证据：![TC01](screenshots/TC01-xxx.png)

## 未覆盖项
无法测试的内容及原因（例如手机未连接、缺少真实 API Key）；没有则写"无"。

## 遗留问题
测试中发现但不在本次范围内的问题。
```

- 报告必须如实记录：不通过的用例写明实际现象，不能省略；无法测试的内容写进"未覆盖项"，不能标为通过。
- 测试完成后，把报告路径、结论和不通过或未覆盖的项发给用户。全部验收标准通过后，把需求文档状态改为"已完成"。
